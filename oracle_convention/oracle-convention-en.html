1. Query Optimization with Index & Partition

1.1. Do NOT use Function on Indexed Column

WRONG - Index will be disabled

❌ Don't-- Index on USER_NAME is ignored
SELECT * 
FROM users 
WHERE UPPER(user_name) = UPPER('john_doe');

-- Index on CREATED_DATE is ignored
SELECT * 
FROM orders 
WHERE TO_CHAR(created_date, 'YYYY') = '2024';

-- Index on MSISDN is ignored
SELECT * 
FROM subscribers 
WHERE SUBSTR(msisdn, 1, 3) = '084';

CORRECT - Index is used effectively

✅ Do-- Normalize data at application layer or use Function-based Index
SELECT * 
FROM users 
WHERE user_name = 'john_doe';

-- Use BETWEEN for date range
SELECT * 
FROM orders 
WHERE created_date >= DATE '2024-01-01' 
  AND created_date < DATE '2025-01-01';

-- Use LIKE with leading character
SELECT * 
FROM subscribers 
WHERE msisdn LIKE '084%';
💡 Explanation:
  • When using function on indexed column, Oracle cannot use B-Tree Index → must do Full Table Scan
  • Function-based Index can be used but has storage and maintenance overhead
  • Best practice: Normalize data before insert/update

1.2. Avoid Operators that Disable Index

WRONG

-- NOT LIKE doesn't use index
SELECT * 
FROM users 
WHERE user_name NOT LIKE 'admin%';

-- NOT IN scans entire table
SELECT * 
FROM orders 
WHERE status NOT IN ('CANCELLED', 'DELETED');

-- <> operator not optimal
SELECT * 
FROM subscribers 
WHERE status <> 'INACTIVE';

-- Leading wildcard doesn't use index
SELECT * 
FROM products 
WHERE product_name LIKE '%phone';

CORRECT

-- Use positive condition
SELECT * 
FROM users 
WHERE user_name LIKE 'user_%' 
   OR user_name LIKE 'customer_%';

-- Use IN instead of NOT IN
SELECT * 
FROM orders 
WHERE status IN ('PENDING', 'PROCESSING', 'COMPLETED');

-- Use equal operator
SELECT * 
FROM subscribers 
WHERE status = 'ACTIVE';

-- Leading character to use index
SELECT * 
FROM products 
WHERE product_name LIKE 'iPhone%';
💡 Explanation:
  • NOT LIKE, NOT IN, <> typically lead to Full Table Scan
  • LIKE '%pattern' (trailing wildcard) cannot use index because starting point is unknown
  • For genuine business requirements needing NOT, consider:
    • Reverse query logic
    • Use Bitmap Index for low cardinality columns
    • Function-based Index if pattern repeats frequently

2. Use IN vs EXISTS

2.1. When to use IN?

Use IN when: Subquery returns FEW records

-- T2 has few records (< 1000)
SELECT s.* 
FROM subscribers s
WHERE s.province_id IN (
    SELECT province_id 
    FROM provinces 
    WHERE region = 'NORTH'
);
Execution Plan:
  1. Full scan T2 (provinces) - small, fast
  2. DISTINCT on province_id
  3. Lookup T1 (subscribers) by index

2.2. When to use EXISTS?

Use EXISTS when: Main table is SMALLER, subquery table is LARGE + has INDEX

-- T1 smaller, T2 large BUT has index on SUBSCRIBER_ID
SELECT o.*
FROM orders o
WHERE EXISTS (
    SELECT 1 
    FROM subscribers s
    WHERE s.subscriber_id = o.subscriber_id
      AND s.status = 'ACTIVE'
);
Execution Plan:
  1. Loop through orders (O) - small table
  2. Each row: Index seek on subscribers(SUBSCRIBER_ID) - fast
  3. Short-circuit when first match found

2.3. Performance Comparison

Scenario IN Performance EXISTS Performance Recommendation
T2 small (< 1K rows), T1 large ⭐⭐⭐⭐⭐ Fast ⭐⭐⭐ Medium Use IN
T1 small, T2 large + indexed ⭐⭐ Slow ⭐⭐⭐⭐⭐ Fast Use EXISTS
Both large ⭐⭐⭐ Medium ⭐⭐⭐ Medium Both equivalent
T2 has duplicates ⭐⭐⭐⭐ (auto DISTINCT) ⭐⭐⭐⭐⭐ (stop at first) Use EXISTS

2.4. Real-world Example

❌ BAD

-- T2 has 10M records, no index
SELECT * 
FROM orders o
WHERE o.subscriber_id IN (
    SELECT subscriber_id 
    FROM subscriber_history  -- 10M rows
    WHERE action_date >= TRUNC(SYSDATE) - 30
);
-- → Full scan 10M rows → DISTINCT → Very slow!

✅ GOOD

-- Reverse logic, use EXISTS with indexed join
SELECT * 
FROM orders o
WHERE EXISTS (
    SELECT 1 
    FROM subscriber_history sh
    WHERE sh.subscriber_id = o.subscriber_id  -- Index seek
      AND sh.action_date >= TRUNC(SYSDATE) - 30
);
-- → Loop orders → Index lookup subscriber_history → Fast!

3. Pagination and Top N Records

3.1. Top N with ROWNUM

Correct way - Sort in subquery first

-- Get top 10 orders with highest value
SELECT * 
FROM (
    SELECT order_id, customer_id, total_amount
    FROM orders 
    ORDER BY total_amount DESC
)
WHERE ROWNUM <= 10;

Wrong way - ROWNUM assigned before sort

-- Only gets first 10 rows, THEN sorts → WRONG!
SELECT * 
FROM orders 
WHERE ROWNUM <= 10
ORDER BY total_amount DESC;
💡 Explanation:
  • ROWNUM is assigned BEFORE ORDER BY executes
  • Must wrap query in subquery to sort first

3.2. Top N with RANK() - Handle TIE

-- Get TOP 10 highest scores, including ties
SELECT * 
FROM (
    SELECT 
        student_id,
        student_name,
        score,
        RANK() OVER (ORDER BY score DESC) as rank_score
    FROM students
)
WHERE rank_score <= 10
ORDER BY rank_score;
Result: 
STUDENT_ID | SCORE | RANK_SCORE
-----------|-------|------------
1001       | 95    | 1
1002       | 95    | 1  ← Same rank
1003       | 94    | 3  ← Skip rank 2
1004       | 94    | 3
1005       | 92    | 5
...

3.3. Pagination with OFFSET-FETCH (Oracle 12c+)

-- Get page 3, 20 records per page
SELECT order_id, customer_id, order_date, total_amount
FROM orders
ORDER BY order_date DESC
OFFSET 40 ROWS FETCH NEXT 20 ROWS ONLY;

-- Page 1: OFFSET 0
-- Page 2: OFFSET 20
-- Page 3: OFFSET 40

For Oracle 11g and below:

-- Pagination with ROWNUM
SELECT * 
FROM (
    SELECT a.*, ROWNUM rnum 
    FROM (
        SELECT order_id, customer_id, order_date
        FROM orders
        ORDER BY order_date DESC
    ) a
    WHERE ROWNUM <= 60  -- page * page_size
)
WHERE rnum > 40;  -- (page - 1) * page_size

4. Working with Partition Tables

4.1. Partition Pruning - Always filter by Partition Key

CORRECT - Partition Pruning

-- Table: ORDERS partitioned by ORDER_DATE (monthly)
-- Only scan partition November 2024
SELECT order_id, customer_id, total_amount
FROM orders
WHERE order_date >= DATE '2024-11-01'
  AND order_date < DATE '2024-12-01'
  AND customer_id = 12345;

-- Execution Plan:
-- PARTITION RANGE ITERATOR (PARTITION: 2024-11)
-- → Only scan 1 partition instead of entire table

WRONG - Full Partition Scan

-- No partition key in WHERE
SELECT order_id, customer_id, total_amount
FROM orders
WHERE customer_id = 12345;

-- Execution Plan:
-- PARTITION RANGE ALL
-- → Must scan ALL partitions → Slow!
💡 Explanation:
  • Partition Pruning = Oracle automatically skips unrelated partitions
  • Always include partition key in WHERE clause to trigger pruning
  • Applies to: SELECT, UPDATE, DELETE

4.2. UPDATE on Partition Table

✅ CORRECT

-- Include partition key
UPDATE orders
SET status = 'COMPLETED'
WHERE order_date >= DATE '2024-11-01'
  AND order_date < DATE '2024-12-01'
  AND order_id = 999888;

❌ WRONG

-- Missing partition key
UPDATE orders
SET status = 'COMPLETED'
WHERE order_id = 999888;
-- → Must scan all partitions to find 1 row

4.3. DELETE on Partition Table

-- WAY 1: DELETE with partition key (Recommended)
DELETE FROM orders
WHERE order_date >= DATE '2024-01-01'
  AND order_date < DATE '2024-02-01'
  AND status = 'CANCELLED';

-- WAY 2: DROP partition (much faster with large data)
-- Only use when need to delete entire partition
ALTER TABLE orders DROP PARTITION orders_202401;
-- → Instant, no UNDO/REDO generated
💡 Performance Tip:
  • DROP PARTITION is 100x faster than DELETE with large datasets
  • Use for archiving/purging old data

4.4. Local Index on Partition Table

-- Table: TRANSACTIONS partitioned by TXN_DATE
-- Local Index: Each partition has its own index

-- Query leverages partition pruning + local index
SELECT * 
FROM transactions
WHERE txn_date >= DATE '2024-11-01'
  AND txn_date < DATE '2024-12-01'
  AND subscriber_id = 'VN0123456789';

-- Execution Plan:
-- 1. Partition Pruning → Only scan partition NOV_2024
-- 2. Local Index Seek on subscriber_id in that partition
-- → Extremely fast!
Index Strategy for Partition Table: 
-- Create Local Index (preferred)
CREATE INDEX idx_txn_subscriber 
ON transactions(subscriber_id) LOCAL;
-- → Each partition has its own index segment
-- → Easy to maintain, balance load

-- Global Index (rarely used)
CREATE INDEX idx_txn_subscriber_global
ON transactions(subscriber_id) GLOBAL;
-- → 1 index for entire table
-- → Complex when add/drop partition

5. Index Strategy

5.1. When SHOULD create Index?

Primary Key & Unique Constraint

-- Automatically creates unique index
CREATE TABLE users (
    user_id NUMBER PRIMARY KEY,
    username VARCHAR2(50) UNIQUE,
    email VARCHAR2(100) UNIQUE
);
-- → Oracle auto-create index on USER_ID, USERNAME, EMAIL

Foreign Key Columns

-- Orders JOIN with Customers very frequently
CREATE INDEX idx_orders_customer 
ON orders(customer_id);

-- Avoid Full Table Scan when JOIN
SELECT o.*, c.customer_name
FROM orders o
  JOIN customers c ON o.customer_id = c.customer_id
WHERE o.order_date >= TRUNC(SYSDATE) - 7;

Frequently Filtered Columns

-- WHERE, ORDER BY, GROUP BY columns
CREATE INDEX idx_orders_date_status 
ON orders(order_date, status);

-- Optimize query pattern:
SELECT * FROM orders
WHERE order_date >= TRUNC(SYSDATE) - 30
  AND status = 'PENDING'
ORDER BY order_date DESC;

5.2. When SHOULD NOT create Index?

Small Tables (< 10,000 rows)

Example: Table PROVINCES (63 rows)
DO NOT need index except PK
Full Table Scan faster than Index Scan with small tables

Low Cardinality Columns

-- Column: STATUS has 3 values (ACTIVE, INACTIVE, DELETED)
-- B-Tree Index not effective
-- If needed: Use BITMAP INDEX

-- Instead of:
CREATE INDEX idx_users_status ON users(status);

-- Use:
CREATE BITMAP INDEX idx_users_status_bmp ON users(status);
-- Only use for low cardinality + infrequent UPDATE

Frequently Updated Columns

Example: Column LAST_UPDATED timestamp update every transaction
Index overhead > Performance gain
Each UPDATE must update Index too → Slow

5.3. Composite Index - Column Order

📌 Rule: Column with highest Selectivity comes FIRST

-- Query pattern:
-- WHERE status = 'ACTIVE' AND created_date >= DATE '2024-01-01'

-- Selectivity:
-- - status: 3 values → Selectivity = 33%
-- - created_date: 365 days/year → Selectivity = 0.27%

-- ✅ CORRECT: created_date first
CREATE INDEX idx_users_date_status 
ON users(created_date, status);

-- ❌ WRONG: status first
CREATE INDEX idx_users_status_date 
ON users(status, created_date);
💡 Explanation:
  • Selectivity = Ability to filter rows
  • Column with high selectivity → Reduce rows to scan early → Faster
  • Rule of thumb: Unique > Date > Status

5.4. Covering Index

-- Frequent query:
SELECT order_id, order_date, total_amount
FROM orders
WHERE customer_id = :customer_id
  AND order_date >= TRUNC(SYSDATE) - 90;

-- ✅ Covering Index: Include all columns in SELECT
CREATE INDEX idx_orders_covering 
ON orders(customer_id, order_date, order_id, total_amount);

-- → Index-Only Scan, no need to access table → Very fast!
Benefits:
  • No need to access table data blocks
  • Reduce I/O operations
  • Increase cache hit rate

5.5. Function-Based Index

-- Query pattern with function:
SELECT * FROM users
WHERE UPPER(email) = UPPER(:email);

-- ✅ Function-based Index
CREATE INDEX idx_users_email_upper 
ON users(UPPER(email));

-- Query must MATCH function in index
SELECT * FROM users
WHERE UPPER(email) = '[email protected]';
⚠️ Trade-off:
  • Pros: Optimize function queries
  • Cons: Increase storage, must maintain, rebuild when modify function

6. MERGE Statement

6.1. Upsert (INSERT or UPDATE)

-- Sync data from staging table → production table
MERGE INTO customers c
USING staging_customers s
ON (c.customer_id = s.customer_id)
WHEN MATCHED THEN
    UPDATE SET 
        c.customer_name = s.customer_name,
        c.email = s.email,
        c.updated_date = SYSDATE
WHEN NOT MATCHED THEN
    INSERT (customer_id, customer_name, email, created_date)
    VALUES (s.customer_id, s.customer_name, s.email, SYSDATE);
💡 Advantages:
  • 1 statement instead of 2 (IF EXISTS → UPDATE ELSE INSERT)
  • Atomic operation
  • Reduce network roundtrips
  • Optimize with bulk operations

6.2. Conditional Update/Insert

-- Only update if value changed
MERGE INTO inventory i
USING (
    SELECT product_id, quantity, unit_price
    FROM temp_inventory
) t
ON (i.product_id = t.product_id)
WHEN MATCHED THEN
    UPDATE SET 
        i.quantity = t.quantity,
        i.unit_price = t.unit_price
    WHERE i.quantity != t.quantity 
       OR i.unit_price != t.unit_price  -- Only update if different
WHEN NOT MATCHED THEN
    INSERT VALUES (t.product_id, t.quantity, t.unit_price);

6.3. MERGE with DELETE

-- Soft delete: Update status = DELETED if not exists in source
MERGE INTO products p
USING temp_products t
ON (p.product_id = t.product_id)
WHEN MATCHED THEN
    UPDATE SET 
        p.product_name = t.product_name,
        p.price = t.price,
        p.status = 'ACTIVE'
WHEN NOT MATCHED BY SOURCE THEN
    UPDATE SET p.status = 'DELETED'
    WHERE p.status = 'ACTIVE';

7. Query Hierarchical Data

7.1. Tree Structure with START WITH ... CONNECT BY

-- Table: CATEGORIES (category_id, parent_id, category_name)
-- Root: parent_id IS NULL

SELECT 
    LEVEL as tree_level,
    category_id,
    LPAD(' ', (LEVEL - 1) * 4, ' ') || category_name as category_display,
    SYS_CONNECT_BY_PATH(category_name, ' > ') as full_path,
    CONNECT_BY_ROOT category_id as root_category_id,
    CONNECT_BY_ISLEAF as is_leaf_node
FROM categories
START WITH parent_id IS NULL  -- Root nodes
CONNECT BY PRIOR category_id = parent_id  -- Parent → Child relationship
ORDER SIBLINGS BY category_name;
Result: 
LEVEL | CATEGORY_DISPLAY        | FULL_PATH
------|------------------------|---------------------------
1     | Electronics            |  > Electronics
2     |     Computers          |  > Electronics > Computers
3     |         Laptops        |  > Electronics > Computers > Laptops
3     |         Desktops       |  > Electronics > Computers > Desktops
2     |     Mobile Phones      |  > Electronics > Mobile Phones

7.2. Recursive CTE (Oracle 11gR2+)

-- Get all subordinates of 1 manager
WITH employee_hierarchy (emp_id, emp_name, manager_id, lvl, path) AS (
    -- Anchor: Root employee
    SELECT employee_id, employee_name, manager_id, 1, employee_name
    FROM employees
    WHERE employee_id = :manager_id
    
    UNION ALL
    
    -- Recursive: Subordinates
    SELECT e.employee_id, e.employee_name, e.manager_id, h.lvl + 1,
           h.path || ' > ' || e.employee_name
    FROM employees e
      JOIN employee_hierarchy h ON e.manager_id = h.emp_id
    WHERE h.lvl < 10  -- Prevent infinite loop
)
SELECT * FROM employee_hierarchy
ORDER BY lvl, emp_name;

8. Clean Code Practices

8.1. Naming Convention

-- ✅ Tables: Plural nouns, lowercase
CREATE TABLE customers (...);
CREATE TABLE order_items (...);

-- ✅ Columns: Singular, descriptive
customer_id NUMBER NOT NULL
customer_name VARCHAR2(100)
created_date DATE DEFAULT SYSDATE

-- ✅ Indexes: idx_{table}_{columns}
CREATE INDEX idx_customers_email ON customers(email);
CREATE INDEX idx_orders_customer_date ON orders(customer_id, order_date);

-- ✅ Primary Keys: pk_{table}
ALTER TABLE customers ADD CONSTRAINT pk_customers PRIMARY KEY (customer_id);

-- ✅ Foreign Keys: fk_{child_table}_{parent_table}
ALTER TABLE orders 
ADD CONSTRAINT fk_orders_customers 
FOREIGN KEY (customer_id) REFERENCES customers(customer_id);

8.2. Query Formatting

❌ BAD: Unreadable

SELECT c.customer_id,c.customer_name,o.order_id,o.order_date,SUM(oi.quantity*oi.unit_price) FROM customers c JOIN orders o ON c.customer_id=o.customer_id JOIN order_items oi ON o.order_id=oi.order_id WHERE o.order_date>=TRUNC(SYSDATE)-30 GROUP BY c.customer_id,c.customer_name,o.order_id,o.order_date;

✅ GOOD: Clean, readable

SELECT 
    c.customer_id,
    c.customer_name,
    o.order_id,
    o.order_date,
    SUM(oi.quantity * oi.unit_price) as total_amount
FROM customers c
  JOIN orders o ON c.customer_id = o.customer_id
  JOIN order_items oi ON o.order_id = oi.order_id
WHERE o.order_date >= TRUNC(SYSDATE) - 30
GROUP BY 
    c.customer_id, 
    c.customer_name, 
    o.order_id, 
    o.order_date
ORDER BY o.order_date DESC;
Formatting Rules:
  • 1 clause per line (SELECT, FROM, WHERE, GROUP BY, ORDER BY)
  • Indent JOIN conditions
  • Align column names vertically
  • Break long lists into multiple lines

8.3. Use Meaningful Aliases

❌ BAD

SELECT 
    a.id, a.name, b.id, b.date
FROM t1 a
  JOIN t2 b ON a.id = b.fk;

✅ GOOD

SELECT 
    cust.customer_id,
    cust.customer_name,
    ord.order_id,
    ord.order_date
FROM customers cust
  JOIN orders ord ON cust.customer_id = ord.customer_id;

8.4. Avoid SELECT *

❌ BAD: SELECT *

SELECT * 
FROM orders o
  JOIN customers c ON o.customer_id = c.customer_id;

Problems:

  • Network overhead with unused columns
  • Ambiguous column names
  • Breaks when schema changes

✅ GOOD: Explicit columns

SELECT 
    o.order_id,
    o.order_date,
    o.total_amount,
    c.customer_name,
    c.email
FROM orders o
  JOIN customers c ON o.customer_id = c.customer_id;

8.5. Use Bind Variables

❌ BAD

-- Hard-coded values (SQL Injection risk + Parse overhead)
SELECT * FROM users 
WHERE username = 'john' 
  AND password = 'pass123';

✅ GOOD

-- Bind variables (Reusable execution plan + Security)
SELECT * FROM users 
WHERE username = :username 
  AND password = :password;
Benefits:
  • Execution plan reuse → Reduce parse time
  • Prevent SQL Injection
  • Reduce library cache fragmentation

9. Anti-Patterns to Avoid

9.1. SELECT in Loop

❌ ANTI-PATTERN: N+1 Query Problem

BEGIN
    FOR rec IN (SELECT order_id FROM orders WHERE order_date = TRUNC(SYSDATE)) LOOP
        -- SELECT in loop → 1000 orders = 1000 SELECTs!
        SELECT customer_name INTO v_customer_name
        FROM customers
        WHERE customer_id = rec.customer_id;
        
        -- Process...
    END LOOP;
END;

✅ SOLUTION: JOIN or BULK COLLECT

SELECT 
    o.order_id,
    c.customer_name
FROM orders o
  JOIN customers c ON o.customer_id = c.customer_id
WHERE o.order_date = TRUNC(SYSDATE);

9.2. Row-by-Row Processing

❌ BAD

FOR rec IN (SELECT * FROM orders WHERE status = 'PENDING') LOOP
    UPDATE orders 
    SET status = 'PROCESSING'
    WHERE order_id = rec.order_id;
END LOOP;
COMMIT;

✅ GOOD

UPDATE orders
SET status = 'PROCESSING'
WHERE status = 'PENDING';
COMMIT;

9.3. DISTINCT instead of correct JOIN

❌ BAD

-- DISTINCT to fix duplicate from bad join
SELECT DISTINCT
    o.order_id,
    c.customer_name
FROM orders o
  JOIN order_items oi ON o.order_id = oi.order_id
  JOIN customers c ON o.customer_id = c.customer_id;
-- → DISTINCT is very resource intensive

✅ GOOD

-- Correct JOIN
SELECT 
    o.order_id,
    c.customer_name
FROM orders o
  JOIN customers c ON o.customer_id = c.customer_id;
-- → Don't need ORDER_ITEMS if only need customer info

9.4. Nested Subqueries (Subquery Hell)

❌ BAD

-- Nested subqueries hard to read
SELECT customer_name
FROM customers
WHERE customer_id IN (
    SELECT customer_id
    FROM orders
    WHERE order_date IN (
        SELECT order_date
        FROM order_dates
        WHERE EXTRACT(YEAR FROM order_date) = 2024
    )
);

✅ GOOD

-- JOIN or WITH clause
WITH recent_dates AS (
    SELECT DISTINCT order_date
    FROM order_dates
    WHERE EXTRACT(YEAR FROM order_date) = 2024
)
SELECT DISTINCT c.customer_name
FROM customers c
  JOIN orders o ON c.customer_id = o.customer_id
  JOIN recent_dates rd ON o.order_date = rd.order_date;

10. Performance Tips

10.1. Use EXPLAIN PLAN

-- Analyze execution plan before deploy
EXPLAIN PLAN FOR
SELECT o.order_id, c.customer_name
FROM orders o
  JOIN customers c ON o.customer_id = c.customer_id
WHERE o.order_date >= TRUNC(SYSDATE) - 30;

-- View execution plan
SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY);
Red Flags in Execution Plan:
  • FULL TABLE SCAN on large tables
  • CARTESIAN JOIN
  • SORT AGGREGATE with large dataset
  • INDEX FULL SCAN instead of INDEX RANGE SCAN

10.2. Collect Statistics Regularly

-- After bulk insert/update/delete
BEGIN
    DBMS_STATS.GATHER_TABLE_STATS(
        ownname => 'SCHEMA_NAME',
        tabname => 'ORDERS',
        estimate_percent => DBMS_STATS.AUTO_SAMPLE_SIZE,
        method_opt => 'FOR ALL COLUMNS SIZE AUTO',
        cascade => TRUE  -- Include indexes
    );
END;
/
When to gather stats:
  • After bulk data load
  • After create/rebuild index
  • Weekly for active tables

10.3. Use Bulk Operations

-- ✅ BULK COLLECT & FORALL
DECLARE
    TYPE t_order_ids IS TABLE OF orders.order_id%TYPE;
    v_order_ids t_order_ids;
BEGIN
    -- Fetch multiple rows at once
    SELECT order_id
    BULK COLLECT INTO v_order_ids
    FROM orders
    WHERE status = 'PENDING'
      AND ROWNUM <= 1000;
    
    -- Update multiple rows at once
    FORALL i IN 1..v_order_ids.COUNT
        UPDATE orders
        SET status = 'PROCESSING',
            updated_date = SYSDATE
        WHERE order_id = v_order_ids(i);
    
    COMMIT;
END;
/
Performance:
  • BULK COLLECT: Reduce context switches between PL/SQL ↔ SQL engine
  • FORALL: Batch DML operations → 10-100x faster vs row-by-row

10.4. Optimize Date Operations

❌ BAD

-- Calculate for each row
SELECT * FROM orders
WHERE TO_CHAR(order_date, 'YYYY-MM-DD') = TO_CHAR(SYSDATE, 'YYYY-MM-DD');

✅ GOOD

-- Calculate once, use BETWEEN
SELECT * FROM orders
WHERE order_date >= TRUNC(SYSDATE)
  AND order_date < TRUNC(SYSDATE) + 1;

10.5. Limit Result Sets

❌ BAD

-- Fetch millions of unnecessary rows
SELECT * FROM transactions
WHERE txn_date >= DATE '2020-01-01';
-- → Could return 10M+ rows!

✅ GOOD

-- Always limit for interactive queries
SELECT * FROM transactions
WHERE txn_date >= TRUNC(SYSDATE) - 30
  AND ROWNUM <= 1000;

-- Or pagination
SELECT * FROM transactions
WHERE txn_date >= TRUNC(SYSDATE) - 30
ORDER BY txn_date DESC
FETCH FIRST 100 ROWS ONLY;

10.6. Avoid Implicit Conversions

❌ BAD

-- Implicit conversion VARCHAR → NUMBER
CREATE TABLE users (
    user_id NUMBER PRIMARY KEY,
    msisdn VARCHAR2(15)
);

SELECT * FROM users WHERE msisdn = 123456789;
-- → Oracle converts 123456789 to '123456789'
-- → Index on MSISDN not used!

✅ GOOD

-- Explicit datatype
SELECT * FROM users WHERE msisdn = '123456789';

10.7. Monitor Long-Running Queries

-- Find queries running > 1 minute
SELECT 
    s.sid,
    s.serial#,
    s.username,
    s.program,
    s.sql_id,
    ROUND(s.last_call_et / 60, 2) as running_minutes,
    sq.sql_text
FROM v$session s
  JOIN v$sql sq ON s.sql_id = sq.sql_id
WHERE s.status = 'ACTIVE'
  AND s.username IS NOT NULL
  AND s.last_call_et > 60  -- > 1 minute
ORDER BY s.last_call_et DESC;

11. Checklist Before Deploy

Pre-Deploy Checklist

  • Explain Plan analyzed
    • No Full Table Scan on large tables
    • Indexes used correctly
    • Join order reasonable
  • Indexes reviewed
    • Partition key included in WHERE clause
    • Composite index column order correct
    • Covering index for high-frequency queries
  • Bind variables used
    • No hard-code values
    • Parameterized queries
  • Result set limited
    • ROWNUM or FETCH FIRST for interactive queries
    • Pagination for large datasets
  • Code reviewed
    • Formatting clean, readable
    • Meaningful aliases
    • Comments for complex logic
  • Testing completed
    • Unit test with sample data
    • Performance test with production-like volume
    • Edge cases covered (NULL, empty, large datasets)

📝 Summary

Key Takeaways

  1. Always think about Index & Partition when writing WHERE clause
  2. Avoid function on indexed columns → Loss of index
  3. Use IN for small subquery, EXISTS for large table with index
  4. Partition pruning = Must-have for partition tables
  5. Clean code = Maintainable code = Happy team
  6. EXPLAIN PLAN = Best friend for performance tuning
  7. Bulk operations > Row-by-row processing
  8. Test with production-like data volume before deploy
